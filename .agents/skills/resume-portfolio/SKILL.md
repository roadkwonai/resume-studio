# Resume Portfolio

사용자가 제공한 이력서와 포트폴리오를 근거로 독립 실행 가능한 웹 이력서를 만든다. 현재 폴더나 상위 폴더에서 `gallery/`와 `templates/`를 찾아 Resume Studio 루트를 확인한다. 설치형 스킬을 사용하는 경우에도 실제 저장소 위치를 찾고 없을 때만 사용자에게 묻는다.

## 자료와 결정

이미 받은 답이나 자료를 다시 묻지 않는다. 이력서, 경력기술서, Notion 및 프로젝트 링크와 사진·PDF를 살피고, 지원 직무, 선택한 템플릿, 대표 프로젝트, 공개 범위, 문의 방식, 배포 여부와 목적 경로를 확인한다. 실제 결과에 영향을 주는 불명확한 부분이나 서로 충돌하는 경력·성과·기간은 묶어서 질문하고 답이 필요한 작업은 기다린다. 독립적으로 할 수 있는 작업은 계속한다. 추측으로 성과, 숙련도, 기술별 연차, 고객이나 운영 여부를 만들지 않는다. 기존 수치와 링크가 실제 자료와 맞는지 확인한다.

템플릿을 지정하지 않았다면 `npm run studio`로 갤러리를 열고 선택을 돕는다. [템플릿 선택 기준](references/templates.md)을 참고한다. 사용자가 명시한 선택이 오래된 `selection.json`보다 우선이다. 자료가 여럿이면 [자료 정리](references/sources.md)를 읽는다. 프로젝트 수와 배치에 사용자의 지시가 있으면 따른다.

## 독립 프로젝트 생성

Resume Studio **저장소 밖**에 사용자별 독립 프로젝트를 만든다. 지정 경로가 없으면 저장소의 형제 디렉터리 `<slug>-resume`을 기본으로 한다. 이미 목적지가 있으면 덮어쓰지 않고 기존 프로젝트인지 확인해 재사용하거나 다른 이름을 정한다. 기존 사이트의 수정은 그 사이트의 실제 경로에서 수행하고 새 프로젝트를 만들지 않는다.

사용자가 기존 완성 사이트와 같은 결과를 새로 만들기를 원하고 소스 프로젝트를 사용할 수 있다면, 기존 앱을 기준으로 안전하게 복사하는 [재현 절차](references/recreate.md)를 우선 적용한다. 기본 템플릿에 프로필만 복사하면 추가한 화면과 메일 기능이 재현되지 않을 수 있다. 다른 템플릿을 원하거나 기존 소스가 없다면 아래 생성 절차를 따른다.

[프로필 가이드](references/profile-guide.md), 선택 템플릿의 `content/README.md`와 `shared/profile.ts`를 읽어 임시 `profile.json`을 작성한 후 형식을 검사한다. 아래 명령은 저장소 루트에서 실행하고, 외부 경로는 절대경로를 쓴다.

```bash
npm run validate -- <profile.json>
npm run new -- <template-id> <slug> <profile.json> </absolute/path/to/slug-resume>
cd </absolute/path/to/slug-resume>
npm install
```

명령이 만든 `.env.example`은 선택 기능의 설명과 빈 값만 있는 템플릿이다. 필요할 때 `.env.local`로 복사하되 기존 환경 파일을 덮어쓰지 않는다. 코드와 환경 파일에서 사용하는 변수명은 반드시 일치시킨다. 사람에 관한 내용은 `content/profile.json`에 두고 사이트 공통 문구만 `content/site.*.json`에 둔다. 생성 앱의 개인정보 파일은 기본적으로 Git에서 제외된다. Git 기반 배포는 공개가 필요한 파일과 보관 방식을 사용자가 명시한 뒤 별도로 구성하고 배포 결과를 검증한다.

프로필 사진, 프로젝트 이미지, 지정한 이력서 PDF는 원본을 보존하며 `public/profile/`에 복사하고 프로필에서 연결한다. URL을 그대로 쓰면 만료되거나 접근이 막힐 수 있는 Notion 이미지는 접근 및 공개 권한을 확인하고 로컬 자산으로 저장한다. 열 수 없는 자료를 읽었다고 주장하지 않는다. PDF에 전화번호·주소 등 공개되는 내용이 있는지 확인해 알리고, 사용자가 지정한 파일과 결과물의 해시를 대조한다. 민감정보는 사용자가 공개하도록 정한 범위만 사용한다.

기존 템플릿의 중요한 시각 요소와 동작을 보존하되, 사용자가 요청한 정보는 템플릿이 지원하지 않으면 독립 프로젝트를 필요한 만큼 수정한다. 지원 직무와 근거에 맞게 프로젝트를 배치하고 프로토타입과 운영 서비스를 구분한다. 기술 스택, 연차 및 성과는 출처가 있는 값만 표기하며 시각적 막대를 쓴다면 의미를 명확히 한다. 링크별 저장소와 서비스 주소를 혼동하거나 없는 URL을 만들지 않는다.

## 문의 및 배포

문의 폼을 요청했으면 실제 발송 방식과 수신 주소를 확인한다. 서버가 없는 GitHub Pages의 정적 사이트만으로 서버 API를 실행할 수 없으므로 기능을 구현할 수 있는 배포 환경이나 외부 서비스를 선택한다. Gmail/Resend 구현, 키 발급 및 Vercel 배포가 필요할 때 [이메일과 환경 설정](references/contact-deployment.md)을 읽는다. 폼만 추가하고 전송이 된다고 말하지 않는다. 배포 및 외부 메일 발송은 사용자 요청 또는 명시된 범위에서만 수행한다.

## 검수와 전달

[검수 절차](references/verification.md)에 따라 출처별 요구 목록과 화면 표시 결과를 각각 대조하고 데이터·원본 디자인·모바일·이미지·버튼·PDF·문의 및 실제 배포 결과를 확인한다. 저장소 루트에서 `npm run verify -- </absolute/path/to/slug-resume>`를 사용하고 독립 프로젝트의 lint/typecheck/build도 실행한다. 실패하거나 검증하지 못한 내용은 숨기지 않는다.

결과로 프로젝트 경로와 실행/배포 주소, 검증 결과, 확인이 필요한 충돌이나 생략, PDF 공개 정보와 남은 제한을 간결하게 알린다. 사용자의 별도 지시 없이 개인 자료나 비밀키를 Resume Studio의 공개 저장소에 커밋하지 않는다.
