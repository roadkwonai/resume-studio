# 기존 완성 사이트 재현

기존 사용자의 독립 프로젝트가 있고 사용자가 같은 사이트의 새 복제본을 원할 때 적용한다. 템플릿 선택이나 사용자 요청이 기존 앱과 다르면 차이를 먼저 확인한다. 기존 앱을 직접 수정하라는 요청에는 복제하지 않는다.

1. 기존 프로젝트의 소스, `content/profile.json`, 자산, 문의 방식과 실제 의존성 및 라우팅을 확인한다. 기존 앱의 경로와 원하는 새 경로를 식별한다. 새 경로가 없으면 저장소 밖에 고르고, 목적지가 이미 존재하면 덮어쓰지 않는다.
2. 승인된 원본 소스와 필요한 사용자 자산만 새 디렉터리에 복사한다. `.git`, `.vercel`, `node_modules`, `.next`, 빌드 캐시, `.omx`, `.env` 및 `.env.*` 등 비밀과 기존 배포 연결 정보는 제외한다. 심볼릭 링크가 프로젝트 바깥으로 향하면 실제 대상을 확인하고 인증정보가 따라가지 않게 한다. `.env.example`은 스킬의 `assets/env.example`을 복사하거나 실제 구현의 비밀 없는 예시로 다시 만든다. 기존 파일, 공개 사이트와 배포 설정은 변경하지 않는다.
3. 새 프로젝트의 Git 제외 설정에 `content/profile.json`, `public/profile/`, `*.pdf`, `.env*`가 있는지 확인하고 `.env.example`만 예외로 둔다. 이 설정은 실수로 Git에 올리는 일을 막을 뿐 웹 배포를 비공개로 만들지는 않는다. Git 배포가 필요하면 사용자가 공개할 파일과 전달 방식을 정하고 실제 배포 결과를 확인한다.
4. 새 디렉터리에서 의존성을 설치하고 코드가 읽는 환경 변수명을 `.env.example`과 대조한다. 값은 복사하지 않으며, 필요할 때 [문의 설정](contact-deployment.md)에 따라 새 프로젝트에 안전하게 설정한다. 문의 API가 유지됐더라도 인증정보가 없으면 발송은 동작하지 않는다.
5. [검수 절차](verification.md)에 따라 원본 사이트와 새 사이트의 내용을 항목별로 대조한다. 특히 카드별 기술 연차와 아이콘, 모든 프로젝트와 이미지·링크, 헤더 버튼, PDF 해시, 문의 방식 및 오류 흐름을 실제 화면에서 확인한다. 새 배포는 요청받은 경우에만 진행한다.
